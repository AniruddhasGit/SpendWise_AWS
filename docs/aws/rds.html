The database, and how it got wired in

What was built on AWS on 25 August 2026, why each choice was made, and how a database sitting in Mumbai ends up serving a page in your browser.

1Why a database at all

SpendWise has to remember things. Expenses, users, categories — none of that survives a restart if it only lives in the app's memory.

It could have run on the PostgreSQL already installed on this laptop. It doesn't, and that's deliberate: the whole product rests on one promise — you cannot see another person's money — and that promise is enforced by a PostgreSQL feature called Row-Level Security. A laptop database where you're the superuser will happily let you read everything, so a test written to prove "user B is denied" would pass without ever testing anything. Green, meaningless.

So: a real database, on a real server, with real permissions. That's what RDS is — Amazon runs the PostgreSQL server, you just say what you want.

3The decision that actually mattered

Inside the server there are two databases and two logins. The two logins are the important part.

LoginJobCan it own tables?
spendwise_ownercreates the tables, runs migrationsyes — it owns them
spendwise_appwhat the running app connects asno

Here's the trap that makes this necessary. In PostgreSQL, the owner of a table can switch off that table's own security rules. One line, and the protection is gone. So if the app connected as the owner, the guarantee would be one command away from being deleted — by a bug, a bad migration, or anyone who got hold of the connection string.

Splitting them means the login that serves your web requests cannot turn off its own restrictions. It doesn't own the tables, isn't a superuser, and holds no bypass privilege. That was checked against the database's own catalogue rather than assumed:

     rolname     | rolsuper | rolbypassrls | rolcreaterole
-----------------+----------+--------------+---------------
 spendwise_app   |    f     |      f       |       f
 spendwise_owner |    f     |      f       |       f

All false. That's the precondition for "user B is denied" being a real test instead of a comforting one.

The second database is spendwise_test. Tests wipe their database clean between runs — pointed at the real one, they'd delete whatever you were working on.

4How it connects to the rest of the app

Nothing in the Python code knows the database's address. It's handed in from outside, and the chain looks like this:

  .env                   two connection strings, never committed to git
    │
    ▼
  app/core/settings.py   reads them, validates them, REFUSES TO START if
    │                    either is missing or malformed
    ▼
  SQLAlchemy engine      opens the actual network connection to Mumbai
    │
    ▼
  repository.py          the only layer allowed to write SQL
    │
    ▼
  service.py  →  router.py  →  your browser

Two connection strings, not one — the owner for migrations, the app for everything else. The app refuses to boot if they're identical, which is exactly what caught a mistake in the CI pipeline earlier today.

DATABASE_URL=postgresql+asyncpg://spendwise_app:***@spendwise-db….ap-south-1.rds.amazonaws.com:5432/spendwise?ssl=require

?ssl=require, not sslmode=require. RDS insists on an encrypted connection. The driver this project uses (asyncpg) spells that option differently from the usual PostgreSQL tools, and gets the spelling wrong in a way that produces a confusing error rather than a clear one.

5What it unlocked

Before: 209 tests were being skipped because there was no database to run them against. A skipped test and a passing test look identical on a green checkmark, which is why they were excluded by name rather than left to quietly skip.

After the schema was applied to both databases:

418 tests · all passed
gate tests (the day-one proof): 12 passed

Including the one that matters most — the proof that a second person's request for someone else's data is refused by the database itself, not by a check in Python that a future bug could skip past.

6Rebuilding it

This is a demo, so it gets torn down and rebuilt. Two things worth knowing:

Stopping an RDS instance is not free and not permanent — storage still bills, and AWS restarts it automatically after 7 days. For a demo, delete rather than stop. Deleting offers a final snapshot; snapshots bill separately, so decline it.

Rebuilding is: create the instance, create the two logins and two databases, run alembic upgrade head, point .env at the new endpoint. Roughly fifteen minutes, most of it waiting.

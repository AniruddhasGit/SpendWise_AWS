1What SpendWise is, and the one promiseA spending tracker where you can only ever see your own money.▶

Someone signs up, types in what they spent, and sees a dashboard of it. That's the whole product. In the client's own words: "a website where people sign up, log what they spend, and see a dashboard of it. Everyone sees only their own money."

Nothing about that is new. What's unusual is how seriously the second half of that sentence is taken. "Everyone sees only their own money" isn't a feature — it's the promise the entire build is arranged around, and you'll see it turn up again in the database design, the tests, and the way the admin screens are deliberately crippled.

Two kinds of person

RoleCan doCannot do
usereverything with their own spendingsee anyone else's, at all
adminreset a password, force a sign-out, deactivate an accountsee what anyone bought or what it cost

That admin restriction is the client's decision, not a technical accident. His words: "That's private, and there's no support reason to look at it. Admin screens show counts and dates, not amounts or descriptions. If I change my mind later I'd rather add it deliberately than find it was there all along."

How that restriction is actually enforced

Not by remembering to leave it out of a screen. The admin can only reach spending data through four special database functions, and those functions declare which columns they are allowed to return — day, total_paise, entries. There is no column a description could arrive in. Even if someone wrote admin code that tried to show it, there's nowhere for the data to come from.

Later the client partly reversed himself (change request CR-001): an admin can now see a person's total over time — how much, per day. Still not what on. The reversal was done by adding a new function with a wider — but still fixed — set of columns.

Money is never a decimal number

₹1,250.00 is stored as the whole number 125000 — the count of paise. Never 1250.00.

The reason, again in the client's words: "Floats can't hold 0.10 exactly and summing them drifts, and this is an app whose entire job is adding numbers up." A computer storing 0.10 as a decimal fraction stores something very slightly off, and adding a thousand of those slightly-off numbers gives you a visibly wrong total. Whole numbers of paise can't drift, because there's nothing smaller to lose.

Where the conversion happens

A text like "1250.00" arrives → Python's Decimal reads it exactly → int(d.scaleb(2)) turns it into 125000 → and it stays a whole number from that point on, through the database and back. It only becomes ₹1,250.00 again in the browser, at the moment of drawing it on screen.

There's even a check that stops anyone reintroducing the bug: a script greps the frontend and fails the build if any file other than the one money file divides by 100.

Four things it deliberately does not do

Not builtWhy not
A phone appout of scope; it's a website
Reading your bank SMSa website literally cannot read your message inbox
Connecting to your bankIndia's Account Aggregator system needs a licence from the RBI. There isn't one
Pulling from Google Pay or Blinkitneither of them hands your transactions to other people's apps

There's also no "forgot my password" email link — because there is no email anywhere in this system, so a reset link would have nowhere to be sent. That's why an admin does it by hand instead.

Why the project works in this document-heavy way at all

Before any code was written, the requirements were frozen and fingerprinted with a checksum, and every decision since has been written down as a numbered file — 154 of them. A decision can never be edited after it's accepted; reversing one means writing a new record that supersedes the old, leaving both readable.

The point is that a year later you can ask "why is it like this?" and get an answer with a date and a name on it, instead of a shrug. There's also a rule that anything genuinely undecided must be labelled OPEN and escalated — inventing a sensible-sounding answer is treated as the worst thing a contributor can do, because an invented answer looks exactly like a real one six months later.

2The map in wordsFour things exist. Three don't, yet.▶

If you only remember one paragraph, make it this one.

There is one program. It serves the web page and answers the data requests, from the same address. You run it as a container. It talks to one database, which is a PostgreSQL server rented from Amazon, sitting in Mumbai. That's it. That's the entire running system.

PieceWhat it isWhere it runs today
The web pageReact, compiled into plain filesinside the container
The APIPython, FastAPIinside the same container
The containerone Docker image holding botha laptop — not AWS yet
The databasePostgreSQL 17.9 on Amazon RDSAWS, ap-south-1 (Mumbai)

Why one program and not two. The obvious way to build this is two separate things — a website on one address, an API on another. That forces you to deal with CORS, a browser rule that blocks a page on one address from quietly calling another. Putting both in one container means the browser only ever talks to a single address, so there is no rule to satisfy and nothing to configure. One deploy instead of two, as well.

The three dashed boxes on the map are the parts that would let this run on AWS instead of a laptop: somewhere to store the built image, a server to run it on, and a bucket for receipt photos. None of them exist yet. Section 11 says exactly what's missing.

3Follow one real clickSign in, then watch the dashboard fetch your total.▶

This is the section that makes the rest make sense. Two requests, start to finish.

Request one: signing in

you type email + password, press Sign in
   │
   ▼  POST /api/auth/login   (a relative path — no hostname anywhere in the code)
the container sees the path starts with /api/ → it is NOT the web page
   │
   ▼  auth router
look up the account by email
   │
   ▼  bcrypt compares the password — on a background thread, ~250 ms
   │     unknown email? it compares against a dummy hash anyway,
   │     so a wrong email and a wrong password take the same time
   ▼
write a row in the sessions table
   │
   ▼  sign a token naming that row, put it in a cookie
Set-Cookie: sw_session=…  httpOnly, SameSite=Lax

httpOnly means JavaScript on the page cannot read the cookie — so a script injected into the page can't steal your session. SameSite=Lax means the browser won't send the cookie when another website triggers the request, which stops a malicious page from acting as you.

Request two: the dashboard asks for your total

The dashboard actually fires five requests at once — the headline totals, the split by category, the day-by-day figures, the list of entries, and your categories. They go in parallel rather than one after another, so the page fills in as fast as the slowest one rather than the sum of all five. Here's one of them:

GET /api/expenses/summary?from=…&to=…     cookie goes along automatically
   │
   ▼  1. check the token's signature is real
   ▼  2. tell Postgres "for this conversation, I am user 7"
   ▼  3. NOW read the session row
   │
   ▼  expenses router → service → repository
   ▼  SQL:  SELECT SUM(amount_paise) … WHERE user_id = 7      ← LOCK 1
   │
   ▼  Postgres checks its own rule on the row: user_id = 7 ?  ← LOCK 2
   │
   ▼  a whole number of paise comes back: 75810
   ▼  React formats it at draw time:  ₹758.10

Those three numbered steps are in that order for a reason, and swapping two of them breaks everything silently. If you read the session row before telling Postgres who you are, the database has no identity to compare against, its rule matches nothing, and the lookup returns zero rows — for every request ever made. Not an error. Just an app where nobody can ever sign in, for a reason that isn't visible anywhere.

The two locks, named exactly

Lock 1 is in the Python: app/modules/expenses/repository.py adds user_id = … to the query — in seven separate places, one per kind of query. The id always comes from your verified token, and never from anything the browser sent. If someone hand-crafts a request with a different user id in the body, it isn't rejected — it's simply ignored, because nothing ever reads it.

Lock 2 is in the database: docs/06 DataModel/security.sql line 43 declares the rule user_id = current_setting('app.user_id', true)::bigint. Postgres applies it to every single read and write on that table, whatever the query says.

Lock 1 alone is the normal way to build this, and it's the one that fails. One forgotten WHERE clause in one query, written at 11pm two years from now, and the promise is gone. Lock 2 doesn't care what the query forgot.

4The app's shapeRouter, service, repository — and why the split is worth it.▶

Every request walks the same short road, through three files that each know one thing.

LayerKnows aboutNever
router.pyURLs, status codes, what the browser sentwrites a database query
service.pythe rules — is this allowed, does it add up—
repository.pySQL, and nothing elseknows it's being used by a website

Why bother? Because when all three live in one file, you end up with a query written inside a web handler, and then a second slightly-different copy of it somewhere else, and after two months you can't change how expenses are read without reading the whole app. Keeping SQL in exactly one place per module means there's exactly one thing to change.

There are six modules — auth, users, expenses, categories, receipts, admin — and a rule that a module only touches its own tables.

The one sanctioned exception, and why it exists

The expense list needs category names, and those live in the categories module. The rule would say "don't join to their table" — but the client asked for the page to load in one request, not two.

So: the expenses repository returns category ids and totals only. The expenses service then asks the categories service for the names — one lookup for the whole page, not one per row. The browser still gets its single request. The rule is still intact. It's written down as a decision (SW-ADR-017) rather than left as a thing someone did.

Four small traps that are load-bearing

Order of routes matters. /api/expenses/summary is declared before /api/expenses/{id}. Otherwise the word "summary" gets captured as an id, which isn't a number, and the endpoint rejects it.

The web-page catch-all is registered last. Registered earlier, it would answer /api/anything with the HTML page and a success code — so a typo'd endpoint would look like a broken response rather than a clear 404.

One database conversation per request. Asking for a second one deliberately raises an error, because "who am I" is set per conversation — a second one would silently see nothing.

Settings load before the server starts. A missing setting stops the program with exit code 78 before it opens the port, rather than failing on the first request that needs it.

5The database, and the two-locks trickSeven tables, and a database that refuses on its own.▶

Seven tables: users, sessions, password_resets, categories, expenses, admin_audit_log, app_meta.

Three of them — sessions, categories, expenses — carry the thing this whole project rests on: Row Level Security.

What Row Level Security actually is

Normally a database hands over whatever the query asks for, and it's the app's job to ask only for your rows. Row Level Security flips that: you attach a rule to the table, and Postgres applies it to every read and write, no matter what the query said. Here the rule is: the row's user_id must match whoever this conversation says it is.

So a query that forgets its WHERE user_id = … doesn't leak everything. It returns nothing.

The trap that makes two database logins necessary. In PostgreSQL, the owner of a table can switch off that table's own security rules — one line, and the protection is gone. So if the running app connected as the owner, the promise would be one command away from deletion, by a bug or a bad migration or anyone who got the password.

LoginJobOwns tables?
spendwise_ownercreates tables, runs migrations, never serves a requestyes
spendwise_appwhat the running app connects asno — and no superuser, no bypass

There's also FORCE ROW LEVEL SECURITY, which closes the same hole from the other side: without it, the owner is exempt from the rules even while they're switched on.

The app checks all this at startup, and refuses to run if it's wrong

On boot the app asks Postgres's own catalogue: is the runtime login a superuser? can it bypass row security? does it own any table? is FORCE missing anywhere? Any yes, and the program stops rather than starting up insecure.

There's a detail here worth stealing. The first version of that check only asked what the login couldn't do — and printed all-green against a login with no privileges whatsoever, which would also have been useless. It now also checks the positive direction: the login must actually be able to read the tables. A check that passes when everything is broken is worse than no check.

Why users deliberately has no such rule

Signing in has to find your account by email before anyone knows who you are. A rule keyed on "who is this request" could never match, because at that moment the answer is "nobody". So users sits outside row security on purpose, and it's recorded as a written-down exception rather than left as a gap someone might later mistake for an oversight. Same for password_resets — redeeming a reset code is by definition something you do when you can't sign in.

Two number traps this schema is shaped around

Sums come back as the wrong type. Postgres returns the sum of a big-integer column as a numeric, which arrives in Python as a Decimal — which is exactly the decimal type the whole project banned. So every sum in the code is explicitly cast back to a whole number.

The cap is on the cast, not the sum. Amounts are limited to 10¹² paise. That isn't because a sum could overflow — it can't — but because converting the result back to a bounded whole number can.

What a "migration" is, and the lock around it

A migration is a numbered file that changes the database's shape — add a table, add a column. They run in order, so any copy of the database can be brought to the current shape by replaying them. This project has two: the whole original schema, and one adding soft account deletion.

They're run with a lock taken first, because two containers starting at the same moment would otherwise both try to change the schema at once. The migration tool does not do this on its own.

There's also a guard that refuses to run migrations if the two database logins are the same — which actually caught a real mistake in the build pipeline.

6The web pageReact, compiled to plain files, served by the same program.▶

React is a way of writing web pages as small reusable pieces. Vite is the tool that turns that source code into plain files a browser understands.

"Building" the frontend means: JSX and CSS go in, and a dist/ folder comes out containing one index.html and some JavaScript and CSS files with scrambled names like index-COdXl4UR.js. The scrambling is deliberate — the name changes whenever the content changes, so a browser can cache them forever without ever serving a stale one.

The Python program then serves that folder. Anything under /assets/ is handed over directly; anything else that isn't an API path gets index.html.

That last bit is why refreshing the page works. If you're on /expenses and hit reload, the browser asks the server for /expenses — a path that doesn't exist as a file. The catch-all hands back index.html, React starts up, sees the address, and draws the right screen. Without it, refreshing anywhere except the home page would 404.

Deliberately small: two dependencies, no router

The frontend has exactly two things it ships to your browser: React and React-DOM. No routing library, no data-fetching library, no state library, no CSS framework.

There's no router because the app is a dashboard and a sign-in screen — the sections are panes, not addresses. A variable holds which pane is showing. The one thing that genuinely is navigable, the date range, is kept in the URL by hand so the Back button returns to the previous period instead of leaving the app.

Nothing in the frontend knows where the API is

Every call is a relative path — /api/expenses, never https://something/api/expenses. There is no configurable address anywhere, and a grep confirms there's no environment variable for one.

That's not laziness; it's the one-container decision showing through. There is nowhere else the API could be, so making it configurable would only create a way to get it wrong.

The one file allowed to do money

rupees(758100) → ₹7,581.00, done by splitting the whole number — never dividing. Indian digit grouping (lakh, crore) comes from the browser's own formatter.

A lint script fails the build if any other file mentions the formatter or divides paise by 100. The rule is enforced by a program, not by remembering.

7The containerWhat Docker actually is, and what this image does on boot.▶

A container is your whole program sealed in a box: the right Python, your code, the built web page, every library, all together. The box runs the same on any machine — which is the entire point.

An image is the sealed box. A container is a running copy of it. You build the image once and run it anywhere.

Two stages, and why

STAGE 1   node:20-alpine
          npm ci  →  npm run build  →  produces client/dist
             │
             │  only this folder crosses over
             ▼
STAGE 2   python:3.12.10-slim
          install Python libraries from requirements.lock
          copy app/, alembic/, the entrypoint
          copy client/dist from stage 1
          →  the final image

Node is needed to build the web page and never to run it. Keeping it in a throwaway first stage means the shipped image has no Node, no npm, no node_modules — smaller, and less in it that could have a security hole.

The version is pinned to the patch: python:3.12.10-slim, not python:3.12. A floating tag means two builds of the exact same commit can differ, weeks apart, for reasons nobody can reconstruct.

What happens when the container starts

set -e                     stop at the first failure, don't limp on
   │
   ▼
alembic upgrade head       bring the database to the current shape
   │                       (with a lock, so two containers can't race)
   ▼
exec uvicorn …:8000        only now does anything listen on a port

Migrations run before the port opens. So a container that can't migrate never accepts a request at all — rather than serving traffic against a half-built database, which is the failure that's genuinely hard to recover from.

Small choices with reasons

Runs as a non-root user, created after the libraries are installed — so the installed libraries are owned by root and the running app can't rewrite its own dependencies.

No COPY . . anywhere. Only named folders are copied in, so nothing can ride along by accident.

curl is installed on purpose, because the health check is written as a curl command and the slim base image doesn't ship one.

The health check points at /healthz, not /readyz. /healthz answers without touching the database. If it checked the database, a two-second blip at RDS would restart a perfectly healthy container.

A 120-second grace period before health checks start counting, because migrations run first and take time on a cold database.

Which processor the image is for

A container image is built for one kind of processor. An image built on an Apple Silicon Mac will not run on an ordinary x86 server — it fails with exec format error.

That failure is unusually nasty, because it arrives late. The push works. The server accepts the job. The container is placed. Then it dies. Everything up to the last step looks like a successful deploy — and until log collection exists, nothing anywhere records the reason.

So the Dockerfile now says which one it wants, and the two stages say different things:

FROM --platform=$BUILDPLATFORM  node:20-alpine      ← whatever you're on
FROM --platform=linux/amd64     python:3.12.10-slim ← must match the server

The first stage runs on your own machine's processor, at full speed, because what it produces is JavaScript — and JavaScript has no processor. The second stage is pinned, because that one ships compiled things: Python itself, and the machine code behind the database driver and the password hasher.

The test that keeps it that way — and how it was proved real

A pin in a file is only as good as the thing stopping someone quietly removing it. So there's a test that reads the Dockerfile as text and fails if the runtime stage isn't pinned.

Adding it broke three existing tests, which matched those same FROM lines with exact patterns — a fair warning that the file is watched more closely than it looks. They were widened to allow a platform prefix, without weakening what they check.

Then the new test was red-proofed, the way section 9 describes: the pin was removed on purpose, the test was watched failing, the pin was put back, and the suite went green again — 17 passing. A test that has never been seen to fail is decoration.

Three things that should be fixed on the database

Backups are set to 1 day, not the 7 that was specified. There are three automatic snapshots and no manual ones, so there's no restore point older than about three days.

Deletion protection is off. Combined with the above, one command destroys the database and all of its backups together.

The instance was created with a starter database called spendwise_dev, while the app uses one called spendwise. Harmless but confusing, and worth checking which one actually holds the data.

Things in the account that no document mentions

A leftover test user with wide permissions granted through a group. A publicly-readable storage bucket from some earlier practice. A stopped server and its disk in a different region, quietly billing. No password rules on the account at all.

None of it is SpendWise. All of it is in the same account as the database that holds people's spending.

9How it proves it worksOne number — 75810 — and the habit of watching tests fail on purpose.▶

The project's proof of life is a single number: 75810.

Four expenses are planted in an empty database — 125000 + 34050 + 210000 + 9999 paise, totalling 379049 — spread across five days. 379049 ÷ 5, rounded, is 75810. If a real browser talking to a real server talking to real Postgres shows ₹758.10, the whole chain works.

Two wrong answers are also checked for by name: 75809 means the rounding was done by chopping instead of rounding up, and 94762 means someone divided by the four entries instead of the five days. Naming the near-misses is what makes the test meaningful — a test that only knows the right answer can pass for the wrong reason.

Red-proofing

Here's the habit worth taking away from this project. A test that has never been seen to fail proves nothing. It might be passing because it's correct, or because it's broken and never actually checks anything.

1  run the isolation test          → green
2  switch OFF the database rule    → deliberately
3  confirm it's really off         → by asking Postgres, not assuming
4  run the test again              → it MUST go red
5  switch the rule back on
6  confirm it's really back on
7  run the test again              → green

If step 4 stays green, the test was decoration. The project's own constitution puts it plainly: "A gate nobody has watched fail is decoration."

A real bug this caught

The first version of the red-proof used the wrong switch — it turned off the "applies to the owner too" setting rather than the rule itself. The test refused to go red, because the running app doesn't connect as the owner, so that setting was irrelevant to it. The red-proof caught its own weakness before it could certify anything false.

The test database is a separate database, and the seeder enforces it

Tests wipe their database clean between runs. Pointed at the real one, they'd delete whatever you were working on. So there are two databases on the same server: spendwise and spendwise_test.

The seeding script refuses to run unless the word spendwise_test appears in the address it was given — and there's a test that hands it the wrong address and checks that it refuses.

Where the counts stand

As of 1 September 2026: 473 tests pass, including 55 that drive a real Chrome browser. The browser suite had never been green before that date — it turned out the test setup was hitting the app's own rate limits, and 34 setups were dying on "too many requests" before they asserted anything.

Milestones: M0 nearly done (9 of 10 — the last one needs a human to sign an observation), M1–M4 complete, M5 (receipts) blocked on storage that doesn't exist, M6 (hardening) mostly still to do.

Why so many generated files

datamodel.json is the one file a human edits. The table definitions, the security rules, the bootstrap script and the traceability sheet are all generated from it. Hand-editing any of those is silently erased by the next build.

The reason is drift: when the same fact is written in four places, three of them eventually become lies, and there's no way to tell which one is current. Generating them means there's only ever one place to change.

Receipts (M5) — blocked on storage. Hardening (M6) — the log deny-list, secret rotation, the full negative suite. And one item in M0 that no program can finish: a human has to run the project from a fresh clone and sign a four-line record saying they watched it work.

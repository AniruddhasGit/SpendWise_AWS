1What changed since version 1The app was on one laptop. Now there are three live copies on the internet.▶

Version 1 of this folder described an app that ran on a laptop, with only its database in the cloud. Everything below is what happened next.

Then (v1)Now (v2)
Ran on a laptopThree copies running on a rented server, reachable from anywhere
One databaseThree databases, one per copy, on the same database server
Deployed by handDeployed by pushing code; the real site still needs a person to press a button
One set of database passwordsSix — a separate pair per copy, and the old shared ones have been switched off
No way to stop a bad changeA change cannot reach the real site without passing the other two first

The three copies are the standard industry arrangement, and they exist for one reason: so that mistakes happen somewhere that does not matter. You try things on the first copy. When it seems right you move it to the second and look again properly. Only then does it go to the one real people use.

Why the app itself barely changed

Almost none of this work touched the application. The app already read its settings from its surroundings rather than from a file baked into it — so the same packed-up app, handed different settings, becomes the dev copy or the real one without a single line differing.

That is not an accident. It was decided long before there was anywhere to deploy to, precisely so that this step would be boring when it arrived.

One real bug was found and fixed along the way. The packed-up app was missing a file it needs when it sets up a brand-new database. The real site never noticed, because its database was already set up and so the code that reads that file never ran. The automated tests noticed immediately — they build an empty database every single time — and they had been failing for four changes in a row before anyone looked.

It is a good illustration of something this project says a lot: the real site working is not evidence that the thing you shipped is correct. It only proves the parts it happened to use.

2The three copiesdev to experiment, uat to rehearse, and the real one.▶

Three separate running copies of exactly the same app, each with its own data.

CopyWhereWhat it is for
devport 8002Where you work. Break it freely; nobody is watching.
uatport 8001The rehearsal. Identical to the real site, so you can check a change properly before anyone sees it.
productionport 8000The real one. The only one with real people's data in it.

"uat" stands for user acceptance testing, which is a heavy name for a simple idea: the place where someone checks the thing actually does what was asked, before it goes live.

On your own computer there are three folders with the same names, each holding the same project pointed at a different one of these. That is why each folder has its own settings file.

Why three folders and not three downloads of the project

They are three views of one project, not three copies. Git can check out several versions of the same repository side by side, sharing one underlying history.

The difference matters: with three real copies you would have three separate histories that slowly drift apart, and you would have to remember to upload changes three times. With this arrangement a change made in one folder is immediately visible from the others, and travels between them by being promoted rather than by being copied.

What "its own database" actually means here

There is one rented database server, and on it three completely separate databases — spendwise, spendwise_uat, spendwise_dev. A row written in one is invisible in the others; they share nothing but the machine they sit on.

Three separate database servers would be cleaner still, and would cost three times as much. For a project like this, separate databases on one server is the right trade — and it is worth knowing that it is a trade, rather than assuming it is free.

3How a change travelsPush to dev. Everything after that is a promotion, not a rebuild.▶

You work on the dev branch. You push. Everything else follows from that.

1 — The checks run. The tests run, the app is packed up, and the whole history of the project is scanned for passwords that should not be there. If any of that is red, nothing below happens at all.

2 — The dev copy updates itself. The newly packed app is uploaded and the dev site is switched over to it. Then the system waits — not for the upload to finish, but for the new copy to actually answer as healthy. A copy that starts and immediately falls over can never be reported as a success.

3 — It gets a mark. Only once dev is healthy does the packed-up app get labelled dev-ok. That mark is the entire basis of the rule in the next section.

4 — You promote it when you are ready. Moving the change onto the uat branch makes the same thing happen there, and then onto main for the real site. Nothing gets rebuilt at either step. The packed-up app that runs on the real site is byte-for-byte the one that ran on dev.

Why never rebuild? If you rebuild for each copy you have three different packed-up apps that ought to be identical. Something as small as a library releasing a new version between two builds makes them differ, and then "we tested it" is no longer true of the thing you shipped. Building once removes the question.

The real site never deploys by itself

Pushing to main deploys nothing. A person has to open the project's web page, choose to run the release, and type the word deploy to confirm. That is the human checkpoint.

Why a typed word instead of a proper approval button

The hosting service does have a real feature for this — a named person has to approve before a release proceeds. It is a paid feature for private projects, and this project is on the free plan.

So the human checkpoint is the trigger itself: nothing reaches the real site unless somebody deliberately goes and starts it. Weaker than a named approver, but real — and the rule in the next section, which is the part that actually prevents accidents, does not depend on it at all.

What happens if you rewrite history instead of promoting cleanly

The gate refuses it, which is correct and worth understanding.

The marks are attached to a specific change, identified by its unique fingerprint. Some ways of merging work produce a new change with a new fingerprint — the same content, a different identity. No copy has ever seen that new thing, so it carries no marks, so it is refused.

That feels annoying the first time. But the thing being promoted is a tested item, and rewriting it makes it a different item that nothing has tested. The gate is right and the instinct is wrong.

4The rule that cannot be talked aroundEach copy leaves a mark only it can leave. The next one refuses to run without it.▶

This is the most important idea in the whole setup, and it is simpler than it sounds.

When a copy of the site deploys successfully, it writes a small label onto the packed-up app: dev-ok, then later uat-ok. Before uat will deploy, it checks that dev-ok is there. Before the real site will deploy, it checks that uat-ok is there. No mark, no deploy.

So if you skip a step — take something straight from dev to the real site — the change arrives carrying no uat-ok mark, and the release stops before it does anything.

Three things make it hold up

PropertyWhy it matters
A mark can be added but never movedNobody can take the mark off an approved item and stick it on a different one. Once written it is permanently attached to those exact bytes.
The real site cannot write marks at allIts permissions do not include writing them. It can only read. So it is physically unable to approve itself.
The mark is only written after the copy is healthyNot after the upload. After the running site answers. A deploy that starts and dies leaves no mark behind.

Why this lives in the image store and not in the code-hosting service. The obvious place to enforce "you can't skip a step" is the service that holds the code — refuse the merge. On this project's plan that is a paid feature, so it is not available.

Putting the rule in the image store turns out to be stronger anyway. Rules in the code-hosting service can be adjusted by whoever administers it. The mark is a fact: either those bytes carry it or they do not, and no setting changes that.

Said honestly: this is not burglar-proof. The dev copy is allowed to write marks, because it writes dev-ok. Which means someone who can already edit the deployment instructions could make dev write a fake uat-ok.

Closing that properly needs a separate image store per copy, so permissions can be drawn tighter. It has not been done, because this gate is aimed at the mistake people actually make — merging into the wrong branch in a hurry — and not at someone who already has the keys and is deliberately misusing them.

A subtle bug in this that was found and fixed

The first version of the marking step looked like it worked. The marks appeared, the gate passed and failed in the right circumstances, and a deliberate test of all three behaviours came back correct.

It was still wrong. A packed-up app is really a small index pointing at the actual contents, and when asked for "the thing called X" the store will politely hand back the contents rather than the index. So the marks were being attached to the contents while the deploy referred to the index — real marks, permanently attached, to a neighbouring object.

The ordering rule was never affected: a mark still only existed if the copy below had genuinely succeeded. What was wrong was the stronger claim that the mark sits on the very thing that ships — a claim that had already been written down as if it had been checked.

It now asks for the item by fingerprint rather than by name, and then re-computes the fingerprint of what came back and refuses to mark anything unless the two match. The earlier test proved the marking worked; it never asked whether it worked on the right object, and only one of those two questions produces an error message.

5The gate, watched failingA rule nobody has seen refuse anything is decoration.▶

This project has a standing rule: a safety check that has never been watched working is not evidence of anything. So the gate was deliberately provoked.

A change was taken to the main branch and released to the real site by hand, having never been through uat. All the tests passed. The release process successfully proved who it was and got its permissions. Then:

success  prove who we are
failure  refuse anything that has not passed uat
skipped  deploy

with this printed out:

REFUSING TO DEPLOY - this commit has not passed uat.

Looked for the mark : uat-ok-cc90b35
Did not find it.

The middle line is the whole point. The release held valid credentials for the real site and was refused anyway — because the refusal does not depend on who is asking. It depends on whether an earlier copy left a mark that only that earlier copy could leave.

The same change was then taken through properly — dev, then uat, then the real site. Same command, same permissions, and this time it went through. The only thing that had changed was that uat had run and left its mark.

Why "it passed the test" is not the same as "the test works"

A check that always says yes passes every time too. You cannot tell the two apart by watching them succeed — only by giving them something that ought to fail and seeing whether they catch it.

This is the same reasoning behind something the project did much earlier: the database rule that stops one person seeing another's money was tested by deliberately switching the rule off and confirming the app broke, then switching it back on and confirming it worked again. Watching something go green proves nothing until you have also watched it go red.

6There are no passwords in the deploymentThe deploy process proves who it is instead of knowing a secret.▶

The usual way to let an automated process touch your cloud account is to give it a permanent key and store it somewhere. This does not do that, and there is no key to steal.

Instead, when a deploy starts, the code-hosting service issues a short-lived signed statement: "this is a job running in the production part of this specific project." The cloud account has been told to trust statements from that service, and to allow exactly one such sentence to unlock each set of permissions. The statement expires when the job ends.

Permanent keyWhat is used here
Works forever until someone revokes itExpires in minutes
Works from anywhereOnly from this one project, in this one copy
Has to be stored somewhereNothing is stored; it is generated per job
Worth stealingWorth nothing five minutes later

Each of the three copies gets its own identity, and each is allowed to touch only its own site. The dev deploy cannot deploy the real site even by accident — not because it is polite, but because it has never been granted that.

The one line that carries all of this, and how it was nearly wrong

The whole boundary rests on the sentence the cloud account is told to accept. A draft version accepted either "a job in the production copy" or "a job on the main branch".

Those look like the same thing and are not. The second one would have granted the real site's permissions to any automated job running on the main branch — including every job anyone adds in future, none of which pass through the human checkpoint. The human checkpoint was the entire point, and accepting the branch as a substitute quietly discards it. Caught by reading it before switching it on.

A second, subtler one cost a failed deploy. The sentence has a documented format, used in every tutorial — and this project happens to have a stricter setting switched on that changes the format, replacing names with permanent numeric identifiers. The written-down format simply never matches, and the error message says only "not allowed", naming nothing. Worth keeping rather than switching off: a name can be given up and claimed by somebody else later; a number cannot.

7Three ways the copies are kept apartDifferent data, different sign-ins, different keys to the safe.▶

"Separate environments" is easy to say and easy to fake. Here is what it actually means in this setup, on three independent axes.

1 — Different data

Three separate databases. Nothing written in one appears in another.

2 — Different sign-ins

Each copy signs its "you are logged in" tokens with its own secret key. A session created on the dev site is meaningless to the real site — not rejected as a matter of policy, but genuinely unreadable, because it was signed with a different key.

3 — Different keys to the safe

Passwords and connection details live in a locked store in the cloud, filed under three separate paths. Each copy is permitted to read only its own path. A dev copy that has been broken into holds nothing that opens the real database — it cannot even read the address.

The third one was not true until today, and the gap is worth describing because it is such an easy one to have.

All three copies were using the same database username and password. Only the database name in the connection string differed. So anything holding the dev credentials could reach the real database by editing one word. That is not separation, it is a naming convention — and it also meant a single leaked password exposed all three at once.

Fixed by giving each copy its own database login, permitted to open one database and refused by the other two. Proved rather than asserted: the dev login was pointed at the real database and the answer was permission denied for database "spendwise".

The trap inside that fix

The obvious way to do it is to make each new login a member of the original shared account, so that all the existing permissions carry over and nothing else has to change.

That would have been theatre. Membership passes down everything, including the right to open the other databases — so all three logins would have reached all three databases and the check would have reported success on the part that worked.

The fix is a setting that says "hold only what you were granted directly, inherit nothing". Each login then gets permission to open exactly one database, and picks up the shared permissions afterwards, once it is already inside. The order matters: the database checks who may come in before any of that happens.

General lesson, worth keeping: whenever separation is built on top of a hierarchy, the question to ask is what the hierarchy hands down for free.

What is still shared, honestly

One physical server runs all three sites, and one database server holds all three databases. If the server fails, all three go down together. If the database server runs out of space, all three notice.

This is the deliberate cost of not paying for three of everything. It is a reasonable trade for a project of this size, as long as nobody mistakes "separate databases" for "separate machines".

8Three sites on one small computerIt fits because somebody measured instead of guessing.▶

The rented server is small — about 916 MB of usable memory. Three copies of the site have to fit in that.

Originally the real site had reserved 512 MB for itself. Measuring what it actually used gave a very different number: 148 to 171 MB. It had reserved roughly three times what it needed, which left only 20 MB spare once the other two copies were added — not enough slack to be comfortable.

CopyReservedCeiling
production384 MB768 MB
uat192 MB384 MB
dev192 MB384 MB
768 of 916148 MB spare

Lowering the real site's reservation to 384 MB — still more than twice what it uses — freed enough room for the other two to live comfortably.

Reserved versus ceiling, and why only one of them matters here

The reserved figure is what gets set aside up front, and it is the number used when deciding whether a copy fits on the machine at all. The ceiling is the point at which the system kills the copy for using too much.

Only the reserved figure was lowered. The ceiling stays high on purpose: lowering it too would shrink the safety margin before a crash while freeing nothing at all, since it was never the number being counted.

Why each deploy has a few seconds of downtime, deliberately

Normally a deploy starts the replacement before stopping the old one, so there is no gap. That needs room for two copies at once — room this machine does not have.

So it is set to stop the old one first. The cost is a few seconds where the site is not there. The alternative is worse than it sounds: with the usual setting the deploy would not fail, it would hang, waiting forever for memory that is never going to appear.

Behind a proper load balancer with room to spare this would be the wrong choice. On one small machine it is the right one.

9What went wrong building thisThirteen mistakes in one day, written down on purpose.▶

This project keeps a folder of its own mistakes. Not a changelog — a record of what somebody believed at the time, and what was actually true. Thirteen went in from this work alone.

Nine of thirteen were caught by reading something back and asking "what would this actually do, line by line?" before running it. The four that were not are the interesting ones.

Two of them leaked a password

Both were code written specifically to avoid printing a secret. Both printed it anyway, on a path nobody had thought about.

The first tried to strip the password out of a connection string and show only the harmless parts. The pattern did not match, and the tool it used passes anything it does not match through unchanged — so "keep only the safe part" failed into "print everything".

The second was a tiny helper function whose name collided with a built-in command. The real command was called instead, could not understand the argument it was given, and printed it inside the error message. The helper never ran at all. The secret came out regardless.

The rule that would have prevented both: a secret should be read and used inside one program and never become an argument, a pipeline step, or a variable in a terminal. Anything that can fail can quote what you handed it.

All of them were changed immediately afterwards, and the old ones now genuinely do not work — checked, not assumed.

Two cost a failed deploy

Both were documents that had been carefully checked for whether they said the right thing, and never checked against the thing they are compared to when they actually run. Reading cannot catch that class of mistake. Only running can — which is the argument for a deployment process that fails loudly and early rather than one that is inspected and then trusted.

The one that had been quietly wrong for weeks

The automated password scan had never once read the project's history. It was set up to — the setting that fetches the full history was there, correctly, and commented as being for exactly that purpose. But that setting controls what gets downloaded, not what the scanner reads, and the scanner had been looking only at each new change as it arrived.

So for weeks it had been answering "is there a password in what you just pushed?" while its own comment, its name, and everyone reading it believed it answered "is there a password in this project?" Anything from before the scan existed had never been examined once.

It was found by accident — triggering the process a different way, which happens to make the scanner read everything. The thing it found was harmless. The fact it had never looked was not.

Why keep a list like this at all. Roughly two thirds of the mistakes recorded across this whole project are failures of noticing rather than failures of code: something was broken and nothing said so. Those are invisible in a list of fixes, because there was never a bug report — just a green tick that meant less than it appeared to.

10What is still not doneThe honest list, including one decision that is not a machine's to make.▶

Gaps stay gaps until they are closed. Here is the current list.

Not doneWhy it matters
No encryption on the connection to the sitesAll three are plain http. Traffic to them can be read in transit. This is a known, recorded weakness, not an oversight — proper certificates need a load balancer or a domain name, and neither exists yet.
One server, one database serverEverything shares hardware. One failure takes all three down.
Marks can be forged by the dev copyDescribed honestly in section 4. Needs a separate image store per copy.
No named approver for releasesA paid feature on this plan. The stand-in is that a person must start the release by hand.
The biggest test is still not automatedThe one proving that one person cannot see another's money still needs a real database to run against. Everything else about this project exists to support that guarantee, and it is still checked by hand.
An old, stale address can still reach the database — fixedA home internet address from weeks ago was still on the permitted list, and those get reassigned to other people. Removed. The database now accepts connections from the app's own server and from nowhere else — not even from the laptop this was built on.

One decision needed a person, and got one. Worth reading as an example of how this project handles a rule that has stopped being true.

There was a written record stating that the automated build process would never touch the cloud account — the owner wanted to do that part by hand, to learn it. That stopped being what happens: it was reversed out loud, under time pressure, and everything on this page was built.

The proper way to change such a record is to write a new one that supersedes it, never to edit the old one. That was attempted and it failed. The project has a checking tool that refuses to let any live document rest on a cancelled decision, and seventeen documents referred to this one — two of them being the original frozen requirements, sealed with a checksum, which by design can never be edited to say "superseded".

So the record could not be superseded at all while the tool worked that way: the only route back to a green check was to leave it marked as current after it had stopped being true. A check that can only be satisfied by lying is worse than no check.

The owner approved a narrow exemption for documents that are sealed and therefore unupdatable — which is a loosening of a safety check, and loosening a safety check is on the short list of things no automated process may decide alone. It was then tested in both directions, because an exemption that quietly disables the whole check would also look like success: superseding the record dropped the failures from seventeen to fifteen (the two that vanished being the two sealed documents), and adding a deliberately unmarked reference elsewhere still failed the check.

The remaining fifteen were real, and each now carries a pointer to the record that replaced it.

Still outstanding from that: the wording around those fifteen pointers has not been rewritten. Several documents still describe the old arrangement in their prose — that the build process touches nothing in the cloud, that nobody ever watches it run — with a "superseded" marker beside it. A reader following the marker gets the right answer; a reader skimming the paragraph does not.

That is editorial work across eleven documents, and it is named here rather than quietly left.

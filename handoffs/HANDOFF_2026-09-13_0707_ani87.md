### The promotion rule, and why it is not in GitHub

This repo is on a free plan, where rulesets and required reviewers are **paid features** — GitHub
literally cannot block a merge here. So the rule lives in ECR:

1. A commit on `dev` is built once and pushed as `sha-<sha>`.
2. When the dev service is **healthy**, the pipeline stamps the image `dev-ok-<sha>`.
3. uat refuses to deploy without `dev-ok-<sha>`; on success it stamps `uat-ok-<sha>`.
4. production refuses without `uat-ok-<sha>`.

Tags are immutable and **the production role has no `ecr:PutImage`** — it cannot approve itself.
Promotion must fast-forward: a squash or rebase makes a new commit that carries no stamps, and the
gate correctly refuses it.

Production deploys **only** by `workflow_dispatch` on `main` with the input `deploy` typed in. A
push to `main` deploys nothing.

## Two secrets leaked, and both are dead

Said plainly because the next session will read the transcript.

- The **shared database passwords** were printed by a `sed` written to redact them — `sed` passes
  non-matching input through unchanged, so "keep the safe part" failed into "print everything".
- All three **`JWT_SECRET`s** were printed by a PowerShell helper named `H`, which collided with the
  built-in alias for `Get-History`; the binding error quoted the value it could not convert. The
  helper never ran.

Both rotated. The old database logins are `NOLOGIN` and verified refused
(`InvalidAuthorizationSpecificationError`). The JWT rotation invalidated every session in all three
environments. **Neither ever reached git** — zero commits, zero tracked files, checked with
`git log -S`.

The rule that would have prevented both, now in `bugs/`: **read and consume a secret inside one
process; never make it an argument, a pipeline element, or a shell variable.** Anything that can
fail can quote what you handed it.
